Personal Brain style · Agent roles v16

Agent roles flow

Claude owns analysis, design, the UI build and integration; Codex starts building the server, data and logic first. Each job takes the smallest route that fits, large work ships in slices, and high risk adds its controls on any route. You confirm requirements, make significant decisions and decide serious review findings. The diagram below shows who does each step and where the work comes back to you.

Pick a route first

Quick

A few files, no new behaviour beyond the ask.

one agent builds + tests→brief report
Bug

A defect that can be reproduced.

discovery→failing test→fix (Claude if UI)→review by risk→report with cause
Feature

One feature on the existing architecture: UI, backend or full-stack.

short plan→approve once→stub→parallel build→review by risk→integrate
Refactor

No change in behaviour; a behaviour change found on the way becomes a Bug or Feature.

discovery→characterization tests→build→review by risk→integrate
Large or new project

New architecture or several features.

analysis + design once→design review→approve
slice: plan→build→review→merge→↺ next slice, planned during review
Review only

You ask for a review.

read-only review→findings by severity + verdict
High risk, on any route

Stored data, migrations, backups, deletion, auth, permissions, privacy, money or external integrations.

risk tests first→you approve the plan→high effort→fresh Codex review + security

A route never removes these. Start on the smallest route and move up when discovery shows more.

The flow, by who does it

You Claude Codex hand-off decision point or "blocked" return parallel input

Rules the diagram doesn't show

Slices, not a waterfall

Large work ships as thin vertical slices, each about a day: plan, build, review, merge. Requirements and design are refined per slice, so a wrong assumption costs one slice.

Risk sets the effort

High risk means the task touches stored data, migrations, backups, deletion, auth, permissions, privacy, money or external integrations. Those workers and their reviews run at high reasoning effort; routine work runs at medium.

Risk cases tested first

Tasks that change stored data get acceptance tests before building for legacy data migration, retry after a partial failure, interrupted or concurrent writes, and inherited permissions, so a review doesn't find them in round 2.

Review by risk

One review covers code and security. A fresh Codex run reviews high-risk branches and every branch Claude wrote; Claude reviews low-risk Codex branches from the diff. The author never gives the final review.

Two review rounds, then Claude decides

Round 2 checks only the fixes; Claude does it when they're small, a fresh reviewer when they're serious. No third round: Claude fixes, accepts, defers or drops each open finding, and you decide security or data-loss ones.

Codex starts first, on a stub

After planning, Claude starts the Codex tasks, then builds the UI against the contract stub (shared types plus a mock API) and reads reports as they arrive.

Self-contained hand-off

Each hand-off carries the worker card as text, the projectId and the recordIds of the task's styles. The worker calls brain_prepare with them directly and never loads this playbook.

Workers keep Personal Brain

Never enabled=false or --disable hooks. Reviews use codex exec --sandbox read-only with the hand-off on stdin, not codex exec review --base.

Claude workers use Code Mode

When Claude hands coding to another Claude, it starts a headless worker in the task worktree: claude -p --settings '{"env":{"CLAUDE_CODE_EXPERIMENTAL_CODE_MODE":"1"}}'. In-session subagents can't use Code Mode.

Reports before diffs

Claude reads each report, its test results and the review verdict, and opens the diff only where a finding, a failed check or a high-risk area points.

What the sandbox can't run

Hand-offs list checks the sandbox blocks, such as browser tests on local ports. Claude runs them, plus the rendered, keyboard and accessibility checks of the UI.

Blocked: one retry

A blocked or timed-out worker gets Claude's decision and one restart. If it's blocked again, Claude takes the task over.

Requirement changes go back

A new or changed requirement goes back through analysis, design and planning, and built work is re-checked against it.
